# VerbaShake — рабочий бриф для Claude Code

Этот файл — точка входа для Claude Code в этом репозитории. Здесь собраны решения,
принятые в обсуждении с Наталией (владелицей проекта) поверх того, что уже написано
в `IMLLS_App_Store_Roadmap.docx` и `REFACTOR_PROMPT.md`. Прочитай сначала их — они
дают полную картину архитектуры и уже проработанный план. Этот файл их не заменяет,
а уточняет и переводит в конкретные задачи.

## Контекст проекта

VerbaShake (изначально IMLLS) — мультиязычное приложение для изучения языков
(английский, украинский, испанский, корейский), сейчас на Streamlit, живёт на
verbashake.streamlit.app. Цель — довести до продакшна и монетизировать (freemium-
подписка), в перспективе — публикация в Google Play / App Store.

Второй репозиторий `imlls` (github.com/Nataliia-Maslova/imlls) — опубликованная
дипломная версия с 3 собственными GEC-моделями (T5, en/es/ko). Этот репозиторий
(`verbashake`) — недоработанный вариант с интеграцией Gemini API вместо GEC-моделей.
Работаем именно с этим репозиторием как с основой.

## Решения, принятые после написания roadmap-дока (важно — они уточняют/переопределяют его)

1. **GEC-модели (`engine/gec.py`) не используем вообще.** Наталья считает их
   недостаточно точными для монетизируемого продукта и не хочет тащить их вес в
   приложение. Grammar correction на платном тарифе — только через
   `engine/gemini.py::correct_grammar` (уже реализовано). `engine/gec.py` и связанные
   зависимости (transformers, torch, скачивание HF-моделей) можно убрать из
   `requirements.txt` и деплоя.

2. **Открытый вопрос дока про Phase 1/3/4 — решён: они платные.** `warmup_question`,
   `generate_practice_test` (live-регенерация), `chat_with_tutor` вызывают Gemini
   вживую и должны попадать под платный тариф — иначе принцип "free = zero live AI"
   из дока сам себе противоречит.

3. **YouTube-ссылки — не динамический поиск, а курируемый статический список.**
   Убираем `find_youtube_videos` (живой вызов YouTube Data API) и связанные с ним
   `generate_youtube_query` / `get_lesson_topic`, используемые именно для видео-
   поиска. Вместо этого — простая таблица (например `data/youtube_links.csv`:
   url, language, level, topic), наполняется вручную/куратором. Ноль вызовов API на
   рантайме.

4. **`engine/curriculum.py` и `engine/adaptive.py` — заменить на настоящий
   recommender.** Сейчас `curriculum.py` строит фиксированную линейную
   последовательность уроков (`advance()` просто +1 к индексу, без учёта
   успеваемости), а `adaptive.py` — RandomForest, который решает не "какую тему
   давать", а только "какую из 3 заготовленных последовательностей шагов
   использовать для конкретной фразы". Ни то, ни другое не решает задачу "куда вести
   пользователя по темам/уровню/типам ошибок, балансируя знакомое и чуть сложное".
   Новый модуль (`engine/recommender.py`) должен это делать.

   Для V1 — **не обучаемая модель, а прозрачная эвристика** (нет данных для
   тренировки на старте): скор кандидата на "что показать следующим" = приоритет по
   SRS (что просрочено к повторению) + разрыв в мастерстве по теме (что слабее всего)
   + бонус за умеренную новизну (чуть выше текущего уровня — ориентир: пользователь
   должен угадывать правильно ~80% случаев, не выше и не ниже). Обучаемую модель
   (contextual bandit / градиентный бустинг) имеет смысл вводить только после
   накопления реальных данных использования.

5. **Логи — облегчить.** `engine/logger.py` сейчас пишет в Google Sheets и локальный
   CSV буквально каждый шаг (timestamp, similarity, response_time_ms, attempts...).
   Наталье это не нужно. Вместо этого — компактная схема: вектор мастерства по
   темам/типам ошибок на пользователя, SRS-состояние (интервал/дата следующего
   повторения) на единицу контента, агрегаты для геймификации (XP, streak). Именно
   этот набор фич нужен recommender'у из пункта 4 — схему логов и схему
   recommender-фич проектировать вместе, не порознь.

6. **Платформа для первого продакшна — веб (без сторов), но собираем как PWA.**
   PWA-обёртка (manifest + service worker) — это просто способ упаковки, а не другая
   архитектура. Собираем фронт сразу как устанавливаемый PWA, но **не подаём в
   Google Play / App Store на первом этапе** — только веб + Stripe Checkout. Это
   убирает необходимость в RevenueCat / App Store & Play Billing и комиссии 15–30%
   на старте, и не требует прохождения ревью сторов. Публикация в сторах (тот же
   код, обёрнутый через Bubblewrap/Capacitor) — отдельный, более поздний этап, когда
   монетизация и retention подтвердятся.

7. **`engine/license.py` / `license_gate.py` — не подходит для подписки.** Это
   привязка лицензии к machine_id (одно устройство = один ключ), а не
   аккаунт-based доступ. Для веб-подписки через Stripe нужен обычный аккаунт
   (email/пароль или magic link) + статус подписки в БД, кросс-девайсный. Точку
   вызова `check_and_gate()` можно оставить как место интеграции, саму логику внутри
   — переписать.

### Фаза C — Recommender и облегчённый прогресс — ГОТОВО, живая БД (2026-08-16)

**Решения, принятые в чате перед реализацией** (важно помнить контекст):
1. Хранилище — забежали вперёд в Фазу D: настоящая Postgres БД (рекомендовала
   Supabase — Postgres + встроенный Auth в одном месте, пригодится для аккаунтов
   в Фазе D), а не Google Sheets и не локальный SQLite (обнулился бы на каждом
   Streamlit Cloud редеплое).
2. Recommender решает и МОДУЛЬ (grammar/vocab/reading), и тему — полная замена
   `curriculum.py`, не только внутримодульный выбор.
3. Теги для Vocabulary (нет уровня) и Reading (нет ни темы, ни уровня) —
   Наталья тегирует вручную через CSV-шаблоны (см. ниже), как с YouTube-CSV в Фазе A.

**Что сделано:**
- [schema.sql](schema.sql) — `content_units` (реестр уроков, единый ID вида
  `grammar:42` / `vocab:Food:12` / `reading:en:7`, гранулярность УРОКА, не фразы —
  так совпадает с тем, что реально запускает UI), `mastery` (EMA правильности по
  теме), `srs_state` (SM-2-lite интервалы повторения), `lesson_pointer` (замена
  "прогресса" из Sheets, ключ `user+target_lang+module` — grammar/vocab/reading
  независимо, как раньше через суффикс `language_pair`), `gamification`
  (перенесённый `gamification.csv` — та же проблема с обнулением на редеплое,
  что чуть не случилась с SQLite, только на CSV, только раньше).
- [engine/db.py](engine/db.py) — подключение через SQLAlchemy, `DATABASE_URL` в
  secrets/env. Универсальный upsert-хелпер.
- [engine/recommender.py](engine/recommender.py) — скор кандидата = `0.5·SRS-
  просрочка + 0.3·(1-mastery) + 0.2·новизна` (веса — константы, не обучены, по
  плану из решения #4). Публичное API: `get_next`, `record_result`,
  `get_stats`, `get_pointer`/`save_pointer`, `reset_user`.
- `engine/gamification.py` — переключен на БД с автоматической разовой миграцией
  из старого CSV при первом чтении пользователя (реальные данные `student1`,
  1490 XP, не потеряются). Если `DATABASE_URL` не настроен — тихо работает на
  CSV как раньше (не ломает то, что уже было, до момента как БД поднимется).
- [scripts/seed_content_units.py](scripts/seed_content_units.py) —
  `--generate-templates` создаёt [data/vocab_tags_template.csv](data/vocab_tags_template.csv)
  (29 строк, по одной на тематический лист) и
  [data/reading_tags_template.csv](data/reading_tags_template.csv) (273 строки —
  English/Ukrainian/Spanish/Korean, остальные 8 языков можно добавить тем же
  форматом позже). Без флага — сидирует `content_units`: Grammar тегируется
  автоматически (`topic_en` + `difficulty`→CEFR из `imlls_database_with_titles.xlsx`,
  173 урока), Vocab/Reading берут level/topic из заполненных шаблонов (553 / 273
  урока — числа сверены с реальным UI). **Важно про Vocab**: lesson_id там не
  сырой из Excel, а глобальный ID, который рантайм строит через
  `vocab_loader._build_global_index()` — сид-скрипт использует ту же функцию,
  иначе ID бы не совпали с тем, что реально открывает приложение.
- Переключены на recommender: `grammar.py`, `reading_app.py`, `path_app.py`
  (полностью переписан — "Coming up" теперь живой снэпшот топ-6 кандидатов, а

  переставить остальные при следующей отрисовке), `app.py` (карточки прогресса
  на лаунчере), `engine/picker.py`, `custom_app.py`, `engine/session.py`.
- **Retired**: `engine/curriculum.py`, `engine/adaptive.py` (тот самый toy

- Найден и починен попутный баг: как в Фазе B, `st.secrets.get(...)` кидает

- Логика проверена автономно (без реальной БД — её у меня нет): парсинг unit_id,
  скоринг-формула на синтетических данных (слабая тема приоритетнее сильной,

### Фаза D — Монетизация — КОД ГОТОВ, ждёт настройки Google/Stripe (2026-08-16)

**Решения, принятые в чате перед реализацией:**
1. LemonSqueezy (`engine/license.py`, `license_gate.py`, verbasake.lemonsqueezy.com) —
   подтверждено черновиком без покупателей, удалён полностью, не мигрирован.
2. Аутентификация — нативный `st.login()`/`st.user` (Streamlit ≥1.42, есть с 1.61)
   через Google как OIDC-провайдера, а не Supabase Auth (Supabase — не
   OIDC-провайдер, для st.login() не подходит напрямую). Даёт настоящий
   cross-device логин с персистентной cookie (переживает обновление страницы,
   в отличие от голого `st.session_state`).
3. `user_id` теперь = `st.user.email` (реальный Google-аккаунт) — заменил
   свободный текст "Your name" во всех 4 местах, где он был (app.py, grammar.py,
   reading_app.py, custom_app.py).
4. Синхронизация подписки со Stripe — **опрос API**, не вебхуки: Streamlit не
   даёт HTTP-эндпоинт для приёма Stripe-событий без отдельной инфраструктуры.
   Статус кешируется в БД (`subscriptions`), перепроверяется через Stripe API
   при логине и когда кеш устаревает (`_STALE_AFTER = 1 час` в `engine/billing.py`).
   Значит отмена подписки может не отразиться до часа — осознанный компромисс
   для V1, апгрейд на вебхуки (например через Supabase Edge Function) —
   отдельная, более поздняя задача, когда появится реальная выручка.
5. Обсуждали более широкий вопрос — не переписать ли всё на другой фреймворк
   вместо Streamlit. Решили остаться: слишком много уже рабочего (recommender,
   Gemini, STT/TTS, геймификация), `st.login()` закрыл главный прежний
   аргумент "за переезд", и это соответствует общему паттерну проекта — не
   усложнять до того, как подтвердится монетизация. Единственное реальное
   больное место — PWA (Фаза E) даётся Streamlit через костыли, но не блокирует.

**Что сделано:**
- `schema.sql` — таблица `subscriptions` (user_id=email, stripe_customer_id,
  stripe_subscription_id, status, plan, current_period_end, checked_at).
- [engine/billing.py](engine/billing.py) — `is_paid()`, `create_checkout_session()`,
  `handle_checkout_return()` (обрабатывает редирект `?checkout=success&session_id=...`
  после оплаты), `_sync_from_stripe()` (опрос Stripe API).
- [engine/auth_gate.py](engine/auth_gate.py) — заменяет `license_gate.py`.
  `check_and_gate()` требует логин (не подписку — приложение бесплатно
  доступно залогиненным, просто без живой генерации Gemini). `current_user_id()`/
  `current_user_name()` — новый источник идентичности везде.
- `engine/gemini.py` — декоратор `@_require_paid` на ВСЕХ 10 публичных функциях
  (warmup_question, evaluate_warmup, correct_grammar, generate_practice_test,

  suggest_alternatives, translate_phrase) — по принципу "free = zero live AI"

**Почему предыдущий фикс не сработал для неё**: он был написан как

**Вопрос про гранулярность "I have" (9+ уроков по лицам/формам) — логично, но
только для этой стадии.** Разбиение по лицам (I/you/we vs he/she,
утверждение/отрицание/вопрос — каждое отдельным уроком) — классический приём
аудиолингвального/структуралистского метода (Pimsleur/Callan): для полного
новичка с почти нулевым словарём нагрузка должна расти на одну переменную за
раз — смешать лица+словарь+порядок слов сразу означало бы захлебнуться. Плюс
"he/she + -s" — типичный источник ошибок, поэтому его осознанно тренируют
отдельно. Это оправдано именно на стадии, когда согласование по лицам само по
себе новый навык — но та же гранулярность уже избыточна там, где этот навык
давно автоматизирован (например "Actions done by others — present/past/future"
разбито на 3 темы просто по шаблону, хотя согласование по лицам к этому
моменту уже не проблема). Гранулярность должна сужаться по мере роста mastery
— это может решать recommender/новый движок конструкций, а не жёсткая
структура данных.

**Источник для обеих задач (пилот на английском, по решению Натальи) — CEFR-J
English Profile** (github.com/openlanguageprofiles/olp-en-cefrj, зеркало
cefr-j.org) — открытая лицензия (коммерческое использование бесплатно с
указанием авторства; C1/C2-словарь от Octanove — CC BY-SA 4.0). Файлы в
[data/cefr_j/](data/cefr_j/) (см. [data/cefr_j/README.md](data/cefr_j/README.md)
— атрибуция). Содержит Vocabulary Profile (headword, pos, CEFR level A1-B2 +
C1/C2-надстройка) и Grammar Profile (~250 структур с CEFR-J уровнем).

**9 подтверждённых пробелов в грамматике imlls** (сверено по Grammar Profile,
не на глаз) — список для будущего дописывания, по приоритету:
1. Reported/Indirect speech (He said that.../She asked if...) — A2-B1.
2. Relative clauses (who/which/that, defining/non-defining) — A2-B2.
3. Conditional 3 (If I had known, I would have...) — C1.
4. Modals of deduction (must/might/could have been) — B2/C1.
5. Used to / would для прошлых привычек — B1.
6. Wish + Conditional 2/3 (I wish I knew.../I wish I had known...) — B1-C1.
7. Phrasal verbs как категория — не встречается вообще.
8. Causative have/get something done — B1-B2.
9. it + be + adj + that/to-infinitive (It's important that.../It's necessary
   to...) — B1-B2.

## Фикс краша на Python 3.9: `TypeError: unsupported operand type(s) for |: 'type' and 'NoneType'` (2026-08-21, продолжение)

Наталья запустила приложение локально (`.venv`, Python 3.9) и получила краш
при импорте `grammar.py` → `engine/session.py` → `class SessionState` (поле
`unit_id: str | None = None`). Причина: аннотации вида `X | None` (PEP 604) в
теле класса/функции вычисляются немедленно при исполнении модуля, если нет
`from __future__ import annotations` — под Python 3.10+ `str | None` работает
(новый синтаксис union), под 3.9 `type.__or__` для этого не определён →
падает сразу при импорте, ещё до какого-либо реального использования кода.
Не связано с сегодняшними правками сессии — это предсуществующий баг,
подсвеченный только сейчас, потому что её `.venv` оказался на 3.9 (раньше,
видимо, работала на более новом Python локально).

**Масштаб оказался шире одного файла** — в проекте уже ЕСТЬ устоявшийся
паттерн (19 файлов используют `from __future__ import annotations` именно
чтобы `X | None` работал на старых Python), но ещё 6 файлов использовали тот
же синтаксис БЕЗ этого импорта:
[engine/session.py](engine/session.py) (сам краш),
[engine/tts.py](engine/tts.py), [engine/vocab_loader.py](engine/vocab_loader.py),
[reading_app.py](reading_app.py), [grammar.py](grammar.py) (6+ мест),
[generate_app_images.py](generate_app_images.py). Починила все 6 — добавила
`from __future__ import annotations` сразу после докстринга в каждом (тот же
паттерн, что уже используется в остальных 19 файлах, поведение кода не
меняет, только откладывает вычисление аннотаций).

**Проверено**: `py_compile` проходит на всех 6 файлов; полный AST-скан всего
репозитория (искала `X | Y` в аннотациях без `from __future__ import
annotations` рядом, за вычетом .venv/venv/сторонних пакетов) — 0 оставшихся
файлов с этим паттерном. **Не проверено вживую** — не запускала `streamlit
run app.py` под Python 3.9 сама (нет такого окружения в песочнице).

## Фикс краша `st.login()`: "400: 'NoneType' object does not support item assignment" (2026-08-21, продолжение)

После двух предыдущих фиксов (Python 3.9 union-синтаксис, недостающие пакеты)
Наталья дошла до экрана логина, нажала "Continue with Google" — экран стал
пустым, URL завис на `localhost:8501/auth/login?provider=<JWT>`, а сам
Streamlit показал `400: 'NoneType' object does not support item assignment`.

**Не в её коде — версийный баг в связке Streamlit↔Authlib.** Прочитала
исходники установленных пакетов (не гадала): `AuthLoginHandler.get()` в
streamlit ловит любое исключение из `client.authorize_redirect(...)` и
показывает его текст как HTTP 400 reason — значит сам `authorize_redirect`
падал. Проследила цепочку до
`streamlit/web/server/oidc_mixin.py::TornadoOAuth2App._save_authorize_data()`
— она намеренно вызывает `self.framework.set_state_data(session=None, state,
kwargs)`, полагаясь на то, что Authlib трогает `session` ТОЛЬКО если кеш не
настроен (у Streamlit кеш всегда настроен — `engine.auth_util.AuthCache`).
Но в `Authlib>=1.6.6` (`FrameworkIntegration.set_state_data`,
`authlib/integrations/base_client/framework_integration.py`) веткa `if
self.cache:` **всё равно** делает `session[key] = {...}` — а `session` там
`None` → `TypeError`. Подтверждено официальным issue
[streamlit/streamlit#13461](https://github.com/streamlit/streamlit/issues/13461)
— Authlib 1.6.5 работает, 1.6.6+ ломает. `requirements.txt` до сих пор был
`Authlib>=1.3.2` без верхней границы — свежая установка (я сама поставила
пакеты в предыдущем фиксе) взяла последнюю 1.6.12 и попала прямо в баг.

**Исправлено**: [requirements.txt](requirements.txt) — `Authlib==1.6.5`
(жёстко, не `>=`, с комментарием почему), переустановлено в её `.venv`.

**Проверено по-настоящему** (не логическим тестом): вызвала
`create_oauth_client("default")` + `client.authorize_redirect(...)` напрямую
в её `.venv` с её реальными secrets.toml — раньше падало с той же ошибкой,
что видела она; после пина Authlib==1.6.5 успешно вернуло настоящий URL
авторизации Google (с её `client_id`, верным `redirect_uri`, PKCE
`code_challenge`, `scope=openid email profile`). Сам клик в браузере и
прохождение до конца (редирект на Google → согласие → возврат в приложение)
— не проверено, это её реальный Google-аккаунт.

## Живая проверка тестового прогона (20 слов, реальный Gemini) + доработка промпта (2026-08-21, продолжение)

Наталья прогнала `--limit 20 --level A1` с реальным ключом, прислала все 20
результатов. Разобрала построчно — нашла 3 системные, повторяющиеся
проблемы (не разовые вкусовщины):

1. **Целевое слово иногда вообще отсутствует в предложении** — "those" →
   "Are there some apples in the box?" (слова "those" нет).
2. **Модель иногда выдаёт вопрос+ответ вместо одного предложения** (4 из
   20 — систематично): "green" → "Where does he buy fruit? He buys fruit in
   a green shop.", "officer" → "What is it? It's an officer.", "should" →
   "This is a boy. The boy should go to school.", "boyfriend" → "Who has a
   boyfriend? - Maria." Причина видна по данным: часть тем imlls сами
   состоят из вопрос-ответных пар ("Do you like coffee? - Yes, I do."),
   которые попадают в промпт как "образец паттерна" — модель копирует их
   двухчастную форму, несмотря на явную инструкцию "верни только одно
   предложение".
3. **Смысловые нестыковки от механического натягивания слова на чужую
   конструкцию**: "under the **blue** tree" (цвет утёк из темы "спрашиваем
   про цвет" и приклеился к случайному существительному), "**green** shop"
   (та же тема про цвет, но целевое слово САМО цвет — двойная путаница),
   "Has she got a good **self**?" (self вне контекста myself/self-esteem
   неестественно как отдельное существительное), "**Be shy!**"
   (повелительное наклонение для черты характера — прагматически странно).

**Исправлено в промпте** (`build_prompt()` в
[scripts/generate_vocab_from_cefrj.py](scripts/generate_vocab_from_cefrj.py)):
явное правило "ровно одно предложение — если образцы вопросы, верни только
вопрос, без ответа"; явное правило "если паттерн не ложится естественно на
слово — адаптируй его, естественность важнее жёсткого соответствия
паттерну" (смягчает проблему 3, не решает полностью — некоторые слова типа
"self" в принципе плохо подходят для изолированной генерации, это
приемлемый остаточный шум, не системная ошибка).

**Добавлена автоматическая проверка** (решает проблему 1): новая
`contains_word()` — регулярка на границы слова, регистронезависимая, ловит
словоформы (learn/learns/learned). `generate_sentence()` теперь проверяет
результат и **делает одну повторную попытку** с усиленным промптом
("в прошлый раз слова не было — обязательно включи его"), если слово
отсутствует; если и повтор не помог — строка всё равно записывается (не
теряем данные), но в консоль печатается `WARNING`, чтобы видеть реальный
процент проблемных слов после полного прогона, а не гадать.

**Проверено** (фейковая модель, реального ключа нет): `contains_word` верно
отличает "those" в "Are there some apples..." (False) от "Those apples are
red." (True), корректно матчит словоформы (learn/learned). Retry-механизм
проверен явно на управляемом сценарии: первый (фейковый) ответ без слова →
автоматически второй вызов с усиленным промптом → второй ответ содержит
слово → возвращается он, без warning. Отдельно проверен противоположный
случай — если и повтор не содержит слово, warning печатается, строка всё
равно возвращается (не теряется).

**Второй тестовый прогон (20 слов, реальный Gemini, обновлённый промпт) —
разобрала, нашла и починила один реальный баг, отменила один свой прошлый
вывод:**

- **Баг в `contains_word()`, не в генерации**: 3 из 4 warning'ов ("Mr./Mr",
  "airplane/aeroplane", "p.m./P.M./pm/PM" — всё та же особенность CEFR-J,
  headword'ы с несколькими написаниями через "/", как уже видели в
  "a.m./A.M./am/AM") оказались ложными — модель сгенерировала верно ("He is
  Mr. Smith.", "This is an airplane.", "She calls me at 8 p.m."), просто
  проверка искала весь составной "mr./mr" одной строкой, которая, конечно,
  никогда не встретится в обычном предложении. **Исправлено**:
  `contains_word()` теперь разбивает headword по "/" и проверяет каждый
  вариант написания отдельно. Проверено на всех реальных случаях из её
  прогона плюс исходном тесте (apples/those) — все 6 совпадают с ожиданием.
- **Отменяю свой прошлый вывод про "две части = плохо"**: в этом прогоне
  двухчастные ответы ("lot" → "Who is it? - It's a lot of people."; "sing"
  → "That's a bird. The bird can sing."; "yellow" → "Where does the sun
  shine? It shines on a yellow car.") при повторном разборе оказались
  вполне естественными способами показать слово в контексте — не дефект
  формата, а нормальный разговорный образец. Была слишком строга в прошлой
  оценке.
- **Единственная реальная шероховатость** — "finish" (noun) → "This is the
  end. The end is a finish." — неестественно, но похоже на разовую
  особенность конкретного слова (существительное "finish" — редкое
  словоупотребление, ближе к "self" из первого прогона), а не системная
  проблема промпта. Мелкие стилистические огрехи такого рода ("twenty" →
  "a twenty-year-old man" не полное предложение; "many" → "Who wants
  many?" слегка неестественно) — ожидаемый уровень шума для 9779
  автоматически сгенерированных предложений, не блокер.

**Вывод**: качество после фиксов достаточное для полного прогона — не
нашла больше системных проблем, только конкретный баг проверки (исправлен)
и штучные шероховатости отдельных слов (приемлемо для V1, можно точечно
почистить позже по мере использования).

## Vocabulary CEFR-J расширен на все языки + фикс "Category" дропдауна (2026-08-22, продолжение)

Наталья предложила: не делать отдельный CEFR-размеченный словник под каждый
target_lang — переводить тот же английский CEFR-J список (headword +

- **`engine/cefr_j_vocab_loader.py::load_cefrj_vocab()`** — теперь всегда
  хранит канонiчное английское предложение в новой колонке `source_en`;
  `native`/`target` заполняются напрямую только когда соответствующий язык
  — English, иначе остаются пустыми под ленивый перевод.

  `_fill_missing_translations()`: тем же `gemini.translate_phrase()` (кеш

  языков, старый `_load_word_bank()` удалён как мёртвый код.
- **`engine/recommender.py`** — `vocab_topic_for_lesson()` и
  `_candidates()` обновлены: рекомендатор тоже считает CEFR-J
  языконезависимым (а не только для English) и безусловно исключает Word

- **`scripts/seed_content_units.py`** — `seed_cefrj_vocab()` теперь ставит

## Phrasebook progress тихо не трекался + module focus для practice (2026-08-22, продолжение)

Наталья спросила, как генерируются Warmup/Practice/Speaking для
Vocabulary и Phrasebook. Разобрала — обе фазы делят один и тот же код
(`phase1_warmup`/`phase3_practice`/`phase4_expression`, `grammar.py`), и
нашла в процессе:

1. **`_MODULE_FOCUS`** (`engine/gemini.py`) — словарь фокуса

   `"phrasebook"` (фокус на фразах/колокаціях, не граматиці/окремих словах).
2. **Реальний, значно серйозніший баг**: `_lesson_level()` для Phrasebook
   завжди падав на грубий lesson_id-фолбек (максимум B1), хоча
   `vocab_tags_template.csv` вже містить реальні CEFR-теги для всіх 203
   phrasebook-юнітів у `content_units` (перевірено напряму в БД). Причина
   виявилась глибшою: `vocab_topic_for_lesson()` викликався лише коли
   `lang_suffix == "vocab"` у ВСІХ 4 місцях запуску уроку (клік по
   картці, кнопка "Next lesson", deep-link по URL, сайдбар "jump to
   lesson") — для Phrasebook `_topic` завжди лишався `None`, тому
   `unit_id_for("phrasebook", ...)` повертав `None`, і **прогрес
   Phrasebook НІКОЛИ не писався в mastery/SRS** з моменту виділення
   модуля (2026-08-21) — тихий, непомітний баг, не пов'язаний з
   сьогоднішньою роботою над CEFR-J.

   Попутно знайшла ще одну регресію від сьогоднішнього переходу
   Vocabulary на CEFR-J: сайдбарна кнопка "jump to lesson" (`grammar.py`,
   ~2872) для vocab викликала СТАРИЙ `vocab_loader.get_topic_for_lesson()`
   напряму по `vocabulary_translated.xlsx` — а CEFR-J lesson_id (100000+)
   в тому файлі просто не існує, тому й ця кнопка для Vocabulary теж
   стала тихо нетрекованою сьогодні.

   **Фікс**: `engine.recommender.vocab_topic_for_lesson()` тепер спочатку
   пробує CEFR-J lookup, а якщо не знайдено — падає на
   `vocab_loader.get_topic_for_lesson()` (той самий global index, що й
   Word Bank, і Phrasebook, і pre-CEFR-J vocab lesson_id — усі три
   покриті одним резолвером). Усі 4 місця запуску уроку тепер викликають
   цей резолвер і для `"vocab"`, і для `"phrasebook"`.
   `_lesson_level()` (`grammar.py`) тепер, перш ніж падати на грубий
   lesson_id-фолбек, шукає `level` у `content_units` за `unit_id`.

   Перевірено на реальних даних (не в браузері — прямий Python +
   пряме SQL до Supabase): `vocab_topic_for_lesson` коректно резолвить
   і Word Bank sheet ("Basic"), і Phrasebook sheet ("Greetings, Basics &
   Courtesy"), і CEFR-J рівень ("A1") для відповідних lesson_id;
   згенерований `unit_id` для phrasebook-уроку 1 точно збігається з
   реальним рядком у `content_units` (`level='A1'`); для юніту 434 з
   реальним тегом `level='C1'` `_lesson_level()` тепер повертає `C1`
   замість жорсткого B1-стелі; фолбек на неіснуючий/непротегований
   `unit_id` коректно повертається до старої lesson_id-евристики, нічого
   не ламає. **Не перевірено вживу в браузері** — сама механіка
   record_result/mastery для Phrasebook з реальним студентом; варто
   пройти хоча б один Phrasebook-урок і перевірити, що mastery/SRS рядки
   з'явились у БД (той самий live-тест, що робили для Фази C).

**Рішення (свідомо інше, ніж для CEFR-J Vocabulary)**: там ліниво
перекладаємо на льоту, бо 9779 слів × N мов — дорого генерувати наперед.

будь-якої нової мови гальмує на десятках живих Gemini-викликів ще ДО

- [scripts/generate_i18n_strings.py](scripts/generate_i18n_strings.py) —
  одноразовий (резюмований) генератор: бере `STRINGS["en"]` як джерело,

  — ці лишаються hand-written) генерує ТІЛЬКИ відсутні ключі (тобто
  es/ko отримують лише свої ~55 бракуючих ключів, а не всі 83 заново) —

  `generate_vocab_from_cefrj.py`), а не paid-gated `translate_phrase()` —
  це одноразовий адмінський скрипт власника, не запит юзера. Резюмованість
  — просто перевіряє, що вже є у вихідному JSON, без окремого
  `load_done()`.
- `engine/i18n.py::_load_generated()` — мерджить згенерований JSON у
  `STRINGS` при імпорті: створює бакет мови, якщо його не було (10 нових
  мов), або домержує лише відсутні ключі (es/ko) — hand-written значення
  ніколи не перезаписуються. `LANG_TO_CODE` розширено до всіх 14 мов

## Phase 5: список каналів замість одного відео (2026-08-23, продовження)

Наталья вживу протестувала попередній результат (скріншот Vocabulary,
Spanish A1) — все спрацювало (мова, рівень, тема, підбір відео), але
помітила: одне й те саме відео повторюється на РІЗНИХ уроках одного рівня

## Фікс: on_lesson_complete() ніколи не викликався — streak завжди "0 days" (2026-08-23, продовження)

Наталья запитала, як зараз записується, що урок пройдено. Розібрала весь
шлях і знайшла реальний, значний баг попутно.

**Що реально працює зараз:**
- Resume-pointer (`lesson_pointer`, для recommender/"Coming up"/My Path) —
  пишеться автоматично в кінці Phase 2 (8-крокового блоку), через
  `_save_step_progress(sess, 99)` → `recommender.save_pointer()`
  (`grammar.py:2946-2947`) — **до** Practice/Speaking/Video, не в самому
  кінці 5-фазної подорожі.
- Mastery/SRS — оновлюється на кожній перевіреній відповіді через
  `LessonSession.score()` → `recommender.record_result()`
  (`engine/session.py:128-146`).
- XP за окремий крок — `on_step_complete()` (`grammar.py:2969`), спрацьовує
  після кожного з 8 кроків Phase 2.

**Знайдений баг**: `on_lesson_complete()` (`engine/gamification.py:562`) —
саме тут рахується денна серія (`_update_streak`), `lessons_completed` і
бонусний XP за весь урок — ніколи не викликався в живому флоу. Єдині два
місця, що його викликали (`render_complete()` `grammar.py:1108` і
`phase5_summary()` `grammar.py:2591`), самі ніде не викликаються з
`main()` — мертвий код, залишок з дизайну до того, як додали Phase
1/3/4/5. Живий шлях Phase 5 ("Назад в головне меню") просто чистив стан
без жодного виклику `on_lesson_complete()`. Це, найімовірніше, і є
причина "🔥 0 days" на кожному скріншоті за весь чат.

**Фікс**: `grammar.py`'s Phase 5 dispatch (`main()`, ~line 3004) тепер
викликає `on_lesson_complete()` при кліку "Назад в головне меню" — той
самий working-паттерн, що вже живий у `reading_app.py:1886-1901`
(підтверджено читанням коду, той виклик реально досяжний з `main()`).
Toast'и (бонус XP / рівень / бейджі / стрік) кладуться в
`_pending_toasts` **після** `_clear_all()` (інакше `_clear_all()` їх одразу
стирає, бо чистить увесь `session_state`) — покажуться на початку
наступного уроку через Phase 2's step loop, той самий "показ із
затримкою" патерн, що вже прийнятий у `reading_app.py` для
`_pending_r_toasts` (не новий компроміс, що я вигадала, а вже наявна
конвенція проєкту).

**Перевірено на реальних даних** (не мок): викликала
`on_lesson_complete()` напряму на тестовому `user_id` проти live
Supabase — `streak_current` 0→1, `lessons_completed` 0→1, видано бейдж
"🌱 First step". Тестовий рядок видалено з `gamification` після
перевірки (`DELETE FROM gamification WHERE user_id = '__test_completion_wiring__'`).
**Не перевірено вживу в браузері** — сам реальний прогін: пройти урок до
кінця (Phase 1→5), клікнути "Назад в головне меню", перевірити що
сайдбар більше не показує "0 days" після повторного проходження в інший
день (стрік по днях — потрібно 2 різні дні, щоб побачити реальний
приріст, а не просто перше "1 day").

**Не займала** (свідомо, поза межами питання): `render_complete()` і
`phase5_summary()` лишаються мертвим кодом — не видаляла, бо це
повноцінні "Lesson Complete!" екрани з банером/персонажем/метриками
(могли бути свідомо відкладені для майбутньої переробки UI, а не просто
забуті), а не тривіальні функції на кшталт `get_hint()`. Видалення —
окреме рішення, не питали.

## Как работать

Двигайся по фазам по порядку — A и B можно делать почти сразу и параллельно, они не
пересекаются. C — самая содержательная и рискованная часть, стоит согласовать схему
данных с Наташей до реализации, а не после. Перед каждой новой фазой — коротко
резюмируй, что сделано, и спроси, продолжать ли в эту сторону — часть решений здесь
(например провайдер STT в фазе B, конкретная модель ценообразования в фазе D)
Наталья ещё не зафиксировала окончательно.
